# src/features/cases

A case, from briefing to debrief (`docs/plan/05-workspace-ui.md`). Public API in `index.ts`, with everything that reads a file or runs the generator behind `server.ts`.

- `loader/` (file 03, server-only through `server.ts`): `source.ts` reads one case file and checks everything that file alone decides — the YAML, the schema, that the story generates, and that every report question's `acceptedEvidence` still matches something. `catalog.ts` is every case in `src/content/cases`, cached in production. `spec.ts` is the one function joining the authoring schema to the generator's input, so the compiler notices if they drift. `loader/evidence.ts` is the browser side: `loadEvidence(caseId)` fetches a case's generated evidence as its own chunk.

  **Headless play** lives here too, because it needs the case file and the generator. `scenario.ts` builds the analyst workstation a case is examined from: the vendored sandbox machine, plus the case's own folder (the signed letter, the handover form and the case file's other `documents`) and its evidence attached under `/dev/evidence`. `play.ts` runs a list of steps against it through the terminal's own `submitLine` — the same parser, engine and **tool registry** as the browser — and grades the report: a finding is `supported`, `needs-evidence` or `not-yet` (`docs/plan/00-overview.md` §4, row 7). `playthroughs.ts` reads the scripted run beside each case, `verify.ts` checks it went as written, and `transcript.ts` prints it. `runnable.ts` (`toRunnableCase`, `getRunnableCase`) turns a case file into the runner's `RunnableCase` when a case page is built: the same workstation headless play uses, the cold open as the briefing, and every `pinned` pattern already resolved into refs, so the browser never needs the schema (full Zod) or the evidence to check an objective. `tests/content/case-browser-play.test.ts` plays the playthrough of each case with a playable page, released or not, through the browser's reducer and holds it to what headless play says. Because play goes through the registry, a tool added in `src/sim/tools/forensics/index.ts` is usable from a playthrough the moment it is registered.

- `run/`: the pure parts. `case-run.ts` is `caseRunReducer` (briefing → workspace → report → debrief), modelled on Hacker Simulation's `missionRunReducer`, plus `toSave`, which picks out what's kept in this browser. `evaluate.ts` is the objective evaluator: the mission schema's `event` and `commandRun`, and the case schema's `pinned`, `reported`, `custody`, `all` and `any`, over the events, the board, the report draft and its citations. `case-definition.ts` is `RunnableCase`, the runner's view of a case; file 03's loader maps a parsed case YAML onto it. `replay.ts` replays a saved command log through the terminal's `submitLine`, for tests and headless play. `use-case-run.ts` holds the reducer in React and saves after every change through `@/lib/case-storage`. `practice-case.ts` and `practice-evidence.ts` are a short case playable with workstation commands, with evidence from the builder, until file 03's fixture case and file 06's Case 1 exist. `catalog.ts` lists every case with a page, and `RELEASED_CASE_LISTINGS` the ones `/cases` offers (the chapter's `released` flags). `evidence.ts` loads a case's evidence with a dynamic `import()`, one shared promise per case (the briefing warms it up), without importing the engine. `workstation.ts` attaches that evidence to the workstation (`evidenceSetup`, run again on Reset machine) and opens a drive for the Evidence Browser through the engine (`browseChange`), on the live session and in replay alike.
- `grading/` (file 10, pure): `gradeReport` and `gradeQuestion`, **the only grader**. The browser's report, the evaluator's `reported` check and headless play all call it. A finding is `supported` only when the answer is right **and** a pin it cites is on the board and in the question's accepted refs; right but uncited, or citing something that doesn't show it, is `needs-evidence`; anything else is `not-yet`. Each finding carries a `reason` (`unanswered`, `incorrect`, `uncited`, `irrelevant`, `supported`) for the debrief's copy. Nothing it takes can see hints, the mentor or how many times the report was submitted.
- `custody/` (file 10, pure): `custodyLog(events, marks)`, the chain of custody as a selector over the engine's events — acquired, hashed (and whether it matched), original read (blocker on or off), recovered, carved, examined, pinned — plus the run's `marks` for what isn't an engine event (a pin from a view, each report submission). `hashedBeforeAnalysing` is the "hashed before opening anything" check on the log's order, reached from a case file as `check: { kind: custody, rule: hashed-before-analysing }`. `describeCustody` and `custodyText` are the words, shared by the Objectives sub-tab, the debrief and the plain-text export stamped SIMULATED.
- `components/`: `CaseRunner` (the page's entry: briefing, and a lazy `case-play.tsx` chunk with everything after Start case), `CaseWorkspace` (the terminal on the left, the tabbed panes on the right; one view at a time on a narrow screen), the Evidence pane (the Evidence Browser from `src/features/evidence-browser`, loaded when the tab first opens, plus what else was handed over), the Objectives pane (a Checklist sub-tab, and a Chain of custody sub-tab), the empty state for the Timeline until file 09 registers it, `report/` (file 10: the case's questions, each with a **Supporting evidence** picker listing the board, then a free summary), `debrief/` (file 10: "n of m findings supported", each answer's verdict with its `explain` only once it's supported, a choice beat's `feedback` line from the cast when one of its other choices was picked, Change your report, and the chain of custody in full with Download the custody record), the blocked-storage banner and the case list.
- `workspace-panes.ts`: the pane registry. **Files 09 (timeline) and 10 (case board) add one line each here** (`{ id, label, load: () => import(...) }`) and nothing else; the Board's line loads `@/features/case-board`. A pane's module default-exports a component taking `WorkspacePaneProps`, which includes the `workstation` — the engine's state, `browse` (the only way a pane reads a drive), `showInTerminal`, and `show(pane, ref?)`, which opens another pane's tab and hands that pane a `reveal` request (the Board's "Show in Evidence Browser" and "Show in timeline"). A pane that can bring an artefact into view reads `reveal`; the Evidence pane passes it to the Evidence Browser, which selects the record on a drive that's already open and never opens one itself.

**Saving.** A save holds the workstation's log (lines typed, Reset machine presses, and drives opened in the Evidence Browser, because opening an original with its write-blocker off changes it), pins and their notes, notes, the report draft and what each answer cites, the custody marks, ticks, hint tiers and story lines played, never the engine's state. Opening a case with a save replays the log through the terminal session before the first paint. When storage is blocked or full, the case plays on and a banner says it won't be kept.

Never import here: another feature's internals, `src/app`, or `localStorage` (use `@/lib/case-storage`). Nothing in `run/` imports React except `use-case-run.ts`.
