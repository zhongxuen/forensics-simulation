## The one-sentence version

A drive is a long row of numbered blocks, split into partitions, and each partition's file system
keeps a record for every file that says what it's called and which blocks hold it.

Think of a library building. The floors are the partitions. Each floor has its own card catalogue,
and the books sit on shelves. An investigator reads the catalogue to find the books, and also walks
the shelves, because a book can still be there after its card is gone.

## Why it matters in security

Every question you ask of a drive, you ask through its structure. "What was in the Documents
folder?" is a question for the file system's records. "Was this file here last week?" is a question
for the times in one record. "Where did the deleted invoice go?" is a question for the free space
between the records.

If you only look the way the computer's owner did, through folders on a screen, you see what the
file system chooses to show: live files, today. An examiner reads the records themselves, deleted
ones included, and the space no record claims.

## How it actually works

### Sectors: the row of blocks

A drive stores everything in <Term id="sector">sectors</Term>, usually 512 bytes each, numbered
from 0. Imaging reads them in order, which is why `acquire` counts its progress in sectors. The
practice laptop's drive has 250,069,680 of them.

### Partitions: the floors

A <Term id="partition">partition</Term> is a run of sectors set aside for one purpose. A table near
the start of the drive says where each one starts and how long it is (Carrier, _File System
Forensic Analysis_, chapter 5). The practice laptop has two: a small "System reserved" partition
starting at sector 2,048, and the "Windows" partition starting at sector 1,050,624, which holds
drive C:.

Carrier also points out that sectors no partition claims are worth a look, since a table can be
edited to hide something. That's one reason you image the whole drive, not one partition.

### File systems: the catalogue

Inside a partition, a <Term id="file-system">file system</Term> decides how files are stored.
Windows uses NTFS, where every file and folder has an entry in one big table, the Master File Table
(Carrier, chapter 11). This game calls each entry a <Term id="file-record">file record</Term>. It
holds:

- the file's name and the folder it's in
- its size and its owner
- four times, which the next lesson is about
- which clusters hold its content

### Clusters: the shelves

A file system hands out space in <Term id="cluster">clusters</Term>, a few sectors grouped
together: 4,096 bytes on this laptop. A 44-byte rota still takes a whole cluster. The record lists
the cluster numbers, and that list is the only thing tying a name to its content.

## Common misconceptions

- **"A drive is one big space for files."** It's a row of sectors, divided into partitions, and
  only a file system turns a partition into files and folders.
- **"If a folder looks empty, the drive has nothing there."** A folder view shows live records.
  Deleted records, and the content they point at, are still on the drive until reused.
- **"Imaging the Windows partition is enough."** Space outside every partition can hold data too.
  Image the whole drive.
- **"The name is the file."** The name lives in the record, the content lives in clusters, and the
  record's cluster list is what joins them. Either half can outlive the other.
