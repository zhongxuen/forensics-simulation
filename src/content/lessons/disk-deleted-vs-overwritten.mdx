## The one-sentence version

Deleting a file marks its record and its space as free without wiping either, so the content can be
read back until another file is written over it, and after that it's gone.

Think of chalk on a board with a label above each drawing. Deleting rubs out the label. The drawing
stays, and anyone who knows where to look can still see it, right up until somebody draws something
new in that spot.

## Why it matters in security

People delete things when something has gone wrong: an invoice, a log, a tool they used. Whether
you can read it back decides what the report can say. It's also a matter of time. A running
computer writes all day without anyone asking it to, and every write might land on the one file you
need. That's why a responder wants a machine left alone, and why imaging comes before anything else.

It matters for how you write, too. "The file was deleted at 11:30 and its content recovered" and
"the file was deleted at 11:30 and has since been overwritten" are both findings. A report that
can't tell them apart, or presents half a file as a whole one, isn't one to rely on.

## How it actually works

### What deleting does

Carrier (_File System Forensic Analysis_, chapter 8) splits a file system's data into categories.
Two matter here: the metadata, meaning each file's record, and the content, stored in data units,
which NTFS calls clusters. Deleting a file changes their status, not their bytes:

- the <Term id="file-record">file record</Term> is marked free, with its name, size, times and
  cluster list left inside it
- its <Term id="cluster">clusters</Term> are marked free and join the
  <Term id="unallocated-space">unallocated space</Term>, with the content still in them
- the record's C time moves to the moment of deletion

### Recovering by record

While the record survives and no other file has taken its clusters, reading those clusters back
gives you the file exactly as it was. That's what `recover` does. It writes a copy into your own
folders and leaves the image untouched.

### Overwritten

The file system is free to give those clusters to the next file that needs space. Once it has,
the old content is gone: the bytes now belong to someone else. The record may still point at the
same cluster numbers, which is the trap. Reading them back would hand you the new file's content
under the old file's name. `recover` checks for this first and refuses, and `inode` says which file
took the clusters.

Partly overwritten is common too: a new file takes some of the clusters and not others. Case 2 has
one of those, and the next lesson shows how to read what's left.

## See it

The practice laptop has three deleted files. One of them, a note, lost its only cluster to a log
file the next morning. Find which, and read back one that survived.

Try `recover train-lt-01 18 --out recovered/old-note.txt` to see the refusal. It names the file
that took the cluster, and points you back at the record, which is still evidence.

## Common misconceptions

- **"Emptying the recycle bin erases files."** It deletes them the same way: the records and
  clusters are marked free, and the content stays until reused.
- **"If the record says which clusters, recovery is always safe."** Only while nobody else owns
  them. Check first, which is what `inode` does.
- **"Overwritten means there's no evidence."** The record, with its name and times, often survives
  and still shows the file existed.
- **"Recovered means original."** A recovered file is a copy of bytes still on the drive. Say where
  it came from: the image, the record number and the clusters.
