## The one-sentence version

Carving searches a drive's raw bytes for the fixed start and end of known file formats and cuts out
what lies between, which finds files that no record points at any more, with no name and no times.

Imagine a box of loose pages with no covers. You can still pull out the letters, because a letter
starts with "Dear" and ends with a signature. You won't know who filed them or when, but you'll
have the letters.

## Why it matters in security

Recovering by record only works while the record survives. When the record has been reused, or the
file system is damaged, nothing on the drive points at the content any more, and yet the bytes can
still be sitting in the free space. Garfinkel's 2007 paper (§1) puts it plainly: carving can
recover files that were deleted and had their directory entries given to other files, as long as
the data itself hasn't been overwritten.

Carving also finds things nobody deleted on purpose: an attachment a mail program unpacked and
cleaned up, a document an application saved a temporary copy of. Those copies can outlive the
original.

## How it actually works

### Signatures

Most file formats begin with fixed <Term id="magic-bytes">magic bytes</Term>, set by the format's
own specification. A PDF starts `%PDF-` and ends `%%EOF`. A ZIP archive starts `PK` followed by the
bytes 03 04. A JPEG photo starts FF D8 FF and ends FF D9.

### Header and footer

<Term id="file-carving">Carving</Term> in its simplest form is what Garfinkel (§5.1.1) calls
header/footer carving: find every place a known start appears, find the matching end after it, and
cut out everything from one to the other. `carve` works this way over the
<Term id="unallocated-space">unallocated space</Term>. An object with a start and no end is marked
partial: something was written over the rest, and what survives can still be read with `strings`.

### What carving can't do

- **No names, no times.** Those were in the file record. A carved file is described by the image,
  its offset in the free space, and its contents.
- **No signature, no carving.** Plain text has no magic bytes, so a deleted text file can't be
  carved this way. Its content is still in the free space; nothing marks where it begins.
- **Pieces.** A file stored in several separate runs of clusters has been through
  <Term id="fragmentation">fragmentation</Term>. A start-to-end carver joins a start to whatever
  follows it, which may belong to another file. Garfinkel (§3.2) found 6% of the files recovered
  from the second-hand drives in his study were fragmented. That's why a carved file has to be read
  and checked before it's relied on.

## See it

The practice laptop's free space holds what three deleted files left behind: a letter draft, a note
since written over, and a PDF handout. Carve it and see what comes out.

Write it out with `carve train-lt-01 --out carved` and read it with `strings`. Then list the
deleted records: record 20 is the same handout, with a name and four times. The carved copy has
neither. The 74 bytes before it are the letter draft (41 bytes) and what overwrote the note (33).

## Common misconceptions

- **"Carving recovers deleted files."** It recovers bytes that look like files. Whether they're the
  file you're after, whole or joined to a stranger's, is something you check.
- **"The file extension tells you the type."** Names can lie and carved files have none. The first
  bytes are what carving goes on.
- **"A carved file's contents give its date."** A date written inside a document is a claim the
  document makes. The drive's own times were in the record.
- **"Carving only finds deleted files."** It searches whatever bytes you give it, so it finds
  copies nobody knew were there.
